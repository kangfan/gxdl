- TapTap 与手机号是两个独立账号。没有自动绑定、合并账号或云存档；同一人选择不同方式会有不同进度。

一、取得 TapTap Client ID / Client Token
1. 打开 https://developer.taptap.cn/ ，完成开发者入驻，创建或选择《古墟大陆》。
2. 游戏服务 > 应用配置 > 立即开启；获取 Client ID、Client Token，地区选择中国大陆。
3. 开通 TapTap 登录。游戏服务 > 基础服务 > 合规认证，按游戏实际情况选择已有/暂无版号并完成平台要求的配置。
4. 登记 Android 包名和签名证书 MD5（32位，去掉冒号）。默认包名为 com.localrebuild.guxudalu；若使用正式包名，请同时修改 AccountConfig 和平台配置。
5. 在 Assets/Resources/Game/AccountConfig.json 填入 clientId/clientToken。不要填写 Server Secret / Master Key。
6. 填入真实可访问的 HTTPS 用户协议 termsUrl、隐私政策 privacyUrl 和 policyVersion。协议须说明 TapTap 认证与独立手机号服务的用途；版本或链接改变后重新征得同意。

官方配置说明：https://developer.taptap.cn/docs/sdk/access/get-ready/
Unity SDK：https://developer.taptap.cn/docs/sdk/integration-guides/unity/
登录：https://developer.taptap.cn/docs/sdk/taptap-login/development-guide/unity/
合规认证：https://developer.taptap.cn/docs/en/sdk/anti-addiction/development-guide/unity/

二、部署独立短信账号服务
运行环境：Node.js 24.x；单实例 Node 服务 + 本地 SQLite + HTTPS 反向代理。
1. 在 Server 目录执行 npm ci --ignore-scripts。
2. 将 .env.example 复制为 .env；生成并保存 AUTH_SECRET：
   node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
3. 在阿里云开通国内短信服务，创建通过审核的短信签名与验证码模板。模板变量为 code，文案有效期为5分钟。
4. 创建仅有 SendSms 所需权限的 RAM 访问凭据，将服务端环境变量 ALIBABA_CLOUD_ACCESS_KEY_ID、ALIBABA_CLOUD_ACCESS_KEY_SECRET、SMS_SIGN_NAME、SMS_TEMPLATE_CODE 填好。不要把这些值放入 Unity 项目或发到聊天里。
5. 运行 npm start；监听 127.0.0.1:8080。按 Caddyfile.example 配置自己的域名、TLS 证书和反向代理。默认只接受可信本机代理传来的 HTTPS 请求；不要把 Node 端口直接暴露到公网。
6. 在 AccountConfig 的 phoneApiBaseUrl 填 https://你的账号域名（不带 /v1/auth）。
7. 将 .env 和 data/accounts.db 及 SQLite sidecar 文件作为服务端敏感数据管理。AUTH_SECRET 必须长期保持稳定并与数据库一同备份；更换会改变手机号哈希，导致已有账号无法按原手机号找回。

阿里云官方 Node SDK：https://help.aliyun.com/zh/sms/developer-reference/using-typescript-openapi-example

接口（均返回 JSON；错误包含 code/message/retryAfterSeconds）
POST /v1/auth/sms/send {"phone":"中国大陆11位手机号"}
 -> {"challengeId":"随机挑战ID","retryAfterSeconds":60}
POST /v1/auth/sms/login {"phone":"...","code":"6位短信验证码","challengeId":"..."}
 -> {"userId":"不透明UUID","accessToken":"会话凭据","expiresInSeconds":86400}
GET /v1/auth/session，Authorization: Bearer <accessToken>
 -> {"userId":"...","expiresInSeconds":剩余秒数}
POST /v1/auth/logout，Authorization: Bearer <accessToken>，body {}
 -> {}

验证码由服务端安全随机生成，只保存带服务端密钥的 HMAC。5分钟过期、单次使用、最多5次错误；同号60秒间隔、每天10次，同IP每小时20次发送，全部服务每天最多1000次发送，同IP15分钟最多30次登录尝试。发送失败同样占用发送限额，防止重试放大费用。原始手机号、验证码和会话 token 不写入日志/数据库。SQLite 存储账号UUID、手机号HMAC、验证码HMAC、会话token HMAC、限流记录。
当前只支持 +86 手机号。生产扩容到多实例/跨机房前，需要共享账号库和限流状态；大规模投放前应按运营需求加短信服务商风控或人机验证及告警。当前实现不含验证码测试后门，测试仅在自动化测试中替换短信发送器。

四、存档
原 gxdl-local-v1.json 不移动、不覆盖，仍供 Editor 本地玩法预览使用。
登录存档为 gxdl-account-<SHA256账号作用域>.json，开场/首破封标记也按账号区分。
没有把旧本地存档自动分配给第一个登录账号；这是为了避免将设备共享进度错误地交给其他账号。

五、外部配置完成后必须做的真机联调
安装/未安装 TapTap 两种授权、取消/失败/重新登录；手机号新注册/老号登录/错码/过期/发送失败；未实名/成年/受限账号；游戏中途时间限制；切后台再回来；退出与账号切换；重启后的存档隔离。当前空配置不能完成这些外部验证，也没有部署线上服务或发送真实短信。

六、登录后的入场流程（2026-11-10）
真实账号登录及合规检查通过后，依次执行 Loading、首次开场、主界面。
Loading 完成需要同时满足真实入场资源准备好、界面进度条显示到 100%。
开场直接播放在独立画面上，结束后才创建主界面。编辑器每次登录都播放开场，忽略已观看记录；打包版本仍只在首次进入时自动播放。
沿用本设备账号隔离的开场记录；自然播放结束或主动跳过记录完成，中断不记完成。
开场右上角显示“跳过动画”按钮；点击后结束当前动画并进入主界面。编辑器再次登录仍播放开场。
加载及开场期间公共游戏入口不可用；限制回调会终止入场并回到登录页。
加载失败或协程被意外停止会显示重试/返回登录。
正式 Loading 已通过 Assets/Scripts/GuxuLoadingScreen.cs 实现 CreateEntryLoadingView，接入既有登录流程；接口说明位于 LOADING-FLOW-CONTRACT.txt。
进度条按真实资源目标平滑推进，到达 100% 并显示 0.35 秒后才进入开场或主界面。
Guxu > QA > Verify Loading Screen 可验证正式界面与入场流程衔接，使用隔离账号门控替身，不请求 SDK 登录或短信；结果和截图见 Reference/Loading20261110。
GXDL > Accounts > Verify Entry Flow 使用编辑器内账号状态和界面替身验证流程，不调用真实登录或短信服务。
测试使用随机隔离账号，并在退出测试时清理对应临时存档和观看标记；结果见 Logs/accounts/entry-flow.txt。
普通 Play 不再跳过登录。只有显式的编辑器离线玩法预览可以直接进入玩法；账号入口始终走入场流程。
